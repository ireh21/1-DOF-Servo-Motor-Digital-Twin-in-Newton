# 디지털 트윈 가이드라인

## 이 문서의 역할

이 문서는 **Newton 기반 디지털 트윈 작업의 큰 흐름을 정리한 개요 문서**다.  
현재 프로젝트 기준으로는 **무부하 단일 서보 모터(1-DOF)** 를 대상으로 설명한다.

이 문서를 읽고 바로 기대할 수 있는 것은 다음과 같다.

- 어떤 순서로 디지털 트윈 작업을 진행하는지 파악
- 어떤 로그와 파라미터가 필요한지 파악
- Newton 모델을 어떤 수준으로 단순화했는지 이해

반대로, 이 문서만으로 바로 재현하기 어려운 것도 분명하다.

- Newton 코드 구현 세부
- 데이터 전처리 스크립트와 입출력 포맷
- 최적화 코드와 하이퍼파라미터
- 다축, 링크, 감속기, 접촉이 있는 복합계 모델링

위 항목들은 프로젝트의 다른 코드, 노트북, 보조 스크립트에 일부 존재할 수 있지만,
이 문서 안에는 설명이 포함되어 있지 않다.

## 1. 목표와 적용 범위

먼저 "무엇을 디지털 트윈할 것인지"와 "왜 하는지"를 분명히 정해야 한다.

현재 프로젝트의 범위는 다음과 같다.

- 대상: **단일 무부하 서보 모터(1-DOF)**
- 목표: **Newton 물리 엔진에서 실측 응답과 유사한 축 응답을 재현**
- 방법: **실측 로그 기반 파라미터 피팅**
- 출력: **위치, 속도, 토크 응답이 맞는 시뮬레이션 모델**


가장 작은 단위의 축 모델을 어떻게 맞추는가에 초점을 둔다.

## 2. 먼저 알아둘 용어

초심자 관점에서는 아래 용어가 먼저 정리되어야 문서가 읽힌다.

| 용어 | 뜻 | 이 문서에서의 역할 |
|---|---|---|
| Command Position | 제어기가 모터에 보낸 목표 위치 | 시뮬레이션 입력 |
| Feedback Position | 실제 모터에서 읽힌 위치 | 시뮬레이션 검증 대상 |
| Feedback Velocity | 실제 모터에서 읽힌 속도 | 시뮬레이션 검증 대상 |
| Feedback Torque | 실제 모터에서 읽힌 토크 관련 값 | 시뮬레이션 검증 대상 |
| Parameter Fitting | 모델 파라미터를 실측에 맞게 조정하는 과정 | 디지털 트윈 핵심 절차 |
| Held-out Log | 피팅에는 쓰지 않고 마지막 검증에만 쓰는 로그 | 과적합 방지 |
| Delay Steps | 지령이 실제 응답에 반영되기 전의 이산 지연 스텝 수 | 제어 지연 표현 |

## 3. 로그와 신호 정의

디지털 트윈은 결국 **입력과 출력의 대응 관계를 맞추는 작업**이므로,  
로그 정의가 불명확하면 이후 단계가 전부 흔들린다.

현재 프로젝트에서는 다음 4개 신호를 사용한다.

| 신호 | 역할 | 비고 |
|---|---|---|
| Command Position | 입력 | 실측과 시뮬레이션 정렬 기준 |
| Feedback Position | 출력 | 위치 오차 평가 |
| Feedback Velocity | 출력 | 속도 응답 평가 |
| Feedback Torque | 출력 | 토크 응답 평가 |

추가 조건은 다음과 같다.

- 샘플링 주기: **1 ms**
- 시간축 정렬 기준: **Command Position**
- 측정 단위: 원본 로그는 `deg` 기준
- 계산 단위: 파라미터 피팅은 `rad` 기준

여기서 중요한 점은 **단위 정합**이다.

- 위치/속도 단위가 로그와 계산식에서 다르면 반드시 변환해야 한다.
- 토크는 서보 드라이브와 모터 정의에 따라 **정격 토크 기준 환산식**이 필요하다.

특히 주의할 점:

- 토크 값이 "실제 Nm"인지, "정격 대비 비율"인지 문서만 보고는 확정하기 어렵다.
- 시간 정렬을 Command Position 기준으로 한다고 했지만, 실제 구현에서 어떤 offset 탐색을 쓰는지는 별도 설명이 필요하다.

## 4. 물리/제어 구조와 파라미터 설계

모델 구조를 먼저 정해야 "무엇을 피팅할지"가 결정된다.

현재 프로젝트의 단일 모터 디지털 트윈 구조는 아래와 같다.

```text
Command Position
    ↓
지령 지연
    ↓
PID 제어기
    ↓
토크 제한 / 토크 응답 지연
    ↓
1-DOF 회전축 동역학
    ↓
Feedback Position / Velocity / Torque
```

포함한 물리는 다음과 같다.

- 1축 회전 관성
- PID 제어
- 지령 지연
- 토크 응답 지연
- 토크 제한
- 열 부하
- 점성 마찰
- 쿨롱 마찰

파라미터는 아래처럼 나눠 보는 편이 읽기 쉽다.

| 분류 | 파라미터 | 설명 |
|---|---|---|
| Drive / Controller | `kp`, `ki`, `kd` | 제어기 이득 |
| Drive / Controller | `delay_steps` | 지령 반영 지연 |
| Mechanical Plant | `inertia` | 유효 관성 |
| Mechanical Plant | `viscous` | 점성 마찰 |
| Mechanical Plant | `coulomb` | 쿨롱 마찰 |
| Torque Dynamics | `torque_response_time_constant` | 토크 응답 지연 |
| Fixed | `integral_max` | 적분기 제한 |
| Fixed | `continuous_torque_limit` | 연속 토크 제한 |
| Fixed | `peak_torque_limit` | 순간 피크 토크 제한 |
| Fixed | `thermal_time_constant` | 열 시정수 |

정리하면 다음 원칙을 따른다.

- **실측 응답에 민감한 파라미터는 피팅 대상**으로 둔다.
- **데이터시트나 사전 설정으로 충분한 값은 고정**한다.

## 5. Newton 모델 구축

3번과 4번에서 정한 구조를 Newton에서 구현하면,  
그 구현체가 곧 디지털 트윈 시뮬레이터가 된다.

구현 방식은 보통 아래 셋 중 하나다.

- Newton 내부 actuator만 사용
- 사용자 코드로 제어기와 물리식을 직접 구현
- 둘을 혼합

현재 프로젝트는 다음 방식을 택한다.

- 구조: **1-DOF revolute joint**
- 제어기, 지연, 토크 제한, 마찰: **사용자 코드에서 직접 계산**
- Newton 역할: **물리계 상태 업데이트**

Newton의 기본 actuator abstraction을 그대로 쓰기보다,  
서보 드라이브 특성을 직접 반영한 torque loop를 별도로 구현했다.

- peak limit와 continuous limit를 분리하고, continuous limit를 RMS thermal state로 관리하고 싶었다.
- 토크 응답 지연을 time constant 파라미터로 명시적으로 두고 피팅하고 싶었다.
- 점성/쿨롱 마찰을 solver 기본 damping과 분리해 식별하고 싶었다.
- WMX 로그 기반 식별에서 제어기와 구동 제한 구조를 한 루프 안에서 투명하게 다루고 싶었다.

현재 구조를 도식으로 다시 쓰면 다음과 같다.

```text
WMX Command Position
        ↓
   지령 지연
 delay_steps
        ↓
서보 드라이브 제어기 근사
 PD 또는 PID
 Kp / Ki / Kd
        ↓
토크 제한
clamping
        ↓
1-DOF Motor Plant
┌─────────────────────┐
│ 관성 J               │
│ 점성마찰 b           │
│ 쿨롱마찰 τc          │
└─────────────────────┘
        ↓
q, q̇, torque
        ↓
WMX Feedback와 비교
```

토크 제한은 한 가지 값으로 끝나지 않는다.

- 피크 토크 제한: 매 제어 주기 하드 클램프
- 연속 토크 제한: 지수 RMS 토크 기반 근사

주의할 점도 있다.

- 열 시정수는 단순화한 근사값이다.
- 실제 드라이브의 과부하 보호 로직과 완전히 같지 않을 수 있다.

## 6. 피팅 전략 설계

모델이 정해졌다고 바로 전체 파라미터를 한 번에 맞추는 것은 비효율적이다.  
보통은 **파형별로 드러나는 특성이 다르기 때문에 단계적으로 접근**한다.

- Stop 로그: 토크 noise floor 파악
- Step 로그: 지연과 과도응답 파악
- Ramp 로그: 속도-토크 관계로 마찰 계수 추정
- Multi-sine 로그: 여러 주파수에서 제어기/관성 응답 확인

## 8. 파라미터 식별

현재 프로젝트에서는 파형별로 식별 절차를 나누어 적용한다.

| 로그 | 주로 보는 것 | 주된 역할 |
|---|---|---|
| Stop | 정지 상태 토크 | 토크 noise floor 확인, deadband 기준 설정 |
| Step | 지령 직후 과도응답 | `delay_steps`, 과도응답 형상 확인 |
| Ramp | 정상속도 구간 속도-토크 관계 | `viscous`, `coulomb` 초기 추정 |
| Multi-sine | 여러 주파수의 추종 응답 | `kp`, `kd`, `inertia` 초기 추정 |

여기서 Multi-sine은 "주파수영역 직접 피팅"이라기보다,  
**여러 주파수의 로그에 대해 Newton 시뮬레이션을 돌리고 시간영역 오차를 비교하는 단계**에 가깝다.

초기 추정 이후에는 Step, Ramp, Multi-sine 정보를 함께 반영해 전체 파라미터를 미세 조정한다.

loss 예시는 다음과 같다.

```text
L = (w_pos·L_pos + w_vel·L_vel + w_trq·L_trq) / (w_pos + w_vel + w_trq)
```

보통은 아래 순서로 진행한다.

1. 전역 탐색으로 초기 후보를 찾는다.
2. 국소 최적화로 세부 파라미터를 조정한다.
3. held-out 로그로 일반화 성능을 확인한다.

예시 알고리즘은 다음과 같다.

- 전역 탐색: `differential_evolution`
- 국소 미세조정: `L-BFGS-B`

토크 오차는 Stop 로그에서 확인한 noise floor를 기준으로  
작은 오차를 deadband 처리할 수 있다.

## 9. 오차 지표와 검증

최소한 아래 항목은 따로 봐야 한다.

- 위치 오차
- 속도 오차
- 토크 오차
- following error
- step 응답 특성
- sine 응답의 gain / phase

중요한 점은 **피팅에 쓴 로그만 잘 맞는 모델은 충분하지 않다**는 것이다.  
반드시 held-out 로그에서 일반화 성능을 봐야 한다.

## 10. 이 문서만으로 가능한 수준과 한계

초심자에 빙의해서 보면, 이 문서만 읽고 가능한 수준은 제한적이다.

### 가능한 것

- 디지털 트윈 작업 순서를 큰 틀에서 이해
- 단일 1축 모터 모델에 어떤 요소가 들어가는지 이해

### 이 문서만으로 어려운 것

- Newton에서 실제로 어떤 API와 데이터 구조로 구현하는지 재현
- 지연, PID, 마찰, 토크 제한을 코드로 정확히 연결
- 토크 환산식을 실제 장비 기준으로 정의
- 로그 정렬과 전처리를 실수 없이 재현
- 최적화 bounds, 초기값, penalty를 설계
- 오차가 "충분히 맞았다"고 판단할 기준 수치 설정

### 더 복잡한 체계로 확장할 때 특히 부족한 점

- 다축 결합항이 없다.
- 중력항이 없다.
- 링크 질량/관성 매핑 절차가 없다.
- 감속기 백래시, 비선형 강성, 유연체 요소가 없다.
- 접촉, 충돌, 외력 상호작용 모델이 없다.
- 센서 지연, 노이즈, 필터 구조가 없다.
- 축 간 제어 결합이나 상위 제어기 구조가 없다.

따라서 **무부하 단일 서보 모터보다 복잡한 체계의 디지털 트윈을 이 문서 하나만으로 수행하기는 어렵다.**  
이 문서는 어디까지나 **1축 축소 모델의 개요**로 보는 편이 맞다.

## 11. 복합계로 확장하려면 추가로 필요한 것

- 로그 전처리 절차

- 감속기, 링크, 중력, 접촉 모델링 방침

## 12. 확장 방향

현재 방향은 다음과 같이 잡을 수 있다.

1. 단일 서보 모터 모델을 안정적으로 맞춘다.
2. 로봇팔의 축별 독립 모델로 확장한다.
3. 이후 축간 결합, 중력, 링크 관성, 감속기, 접촉을 단계적으로 추가한다.
